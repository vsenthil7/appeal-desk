## Why this happened

The Devvit developer dashboard surfaces a banner whenever the project's
`@devvit/public-api` minor lags the installed CLI:

> *"A new version of Devvit (0.13.0) is now available. Please update to the
> latest version and upload a new build of your app."*

Our CLI is 0.13.0; our project was pinned to `@devvit/public-api: "0.11.x"`.
The banner is asking for a runtime bump.

## What I tried first \u2014 and why I changed course

**First attempt: bump straight to 0.13.0.** That **failed.** Devvit 0.13 is
not a routine minor bump from 0.11:

- The Blocks (custom-post) API was removed from `@devvit/public-api` in 0.13
  and moved into the new `@devvit/web` package.
- `JSX.Element` / `JSX.IntrinsicElements` ambient namespace removed.
- Hooks `useState`, `useAsync`, `useForm` no longer exported from
  `@devvit/public-api`.
- `Devvit.addCustomPostType`, `Devvit.CustomPostComponent`,
  `SubmitPostOptions.preview` all removed.

That would require rewriting the entire `.tsx` shell against `@devvit/web`'s
new web-view architecture (Express + Devvit client + iframe). Realistic
estimate: 4-6 hours. Not feasible before the AT-Hack0022 deadline.

**Course correction: target 0.12.24 instead.** 0.12.x is the last minor
that still supports the classic Blocks/custom-post API in `@devvit/public-api`.
It's the natural "current stable" target for a 0.11-era project, and:

- `npx tsc --noEmit` passes with **zero source changes** (Blocks API
  identical between 0.11.19 and 0.12.24).
- All 288 tests pass.
- Coverage gate passes.
- `devvit upload` succeeds and produces v0.0.3.

## Future migration to 0.13.x / `@devvit/web` (deferred)

A real 0.13 migration means switching the dashboard from Blocks (server-side
JSX rendered by Devvit) to `@devvit/web` (a real web view served as an
iframe inside Reddit). Steps for a future sprint:

1. Read the official 0.12 \u2192 0.13 migration guide on developers.reddit.com.
2. Add the `@devvit/web` dep alongside `@devvit/public-api` 0.13.
3. Convert `AppealsDashboardPost.tsx` from a Blocks component to a web view
   (likely Vite + React in a separate folder).
4. Rewire `Devvit.addCustomPostType` \u2192 web-view post type.
5. Migrate forms (`useForm`) to the web-view forms API.
6. Migrate triggers + scheduler (these are mostly unchanged \u2014 they live
   on Devvit, not in the post).
7. `devvit upload` v0.1.0.

The core layer (`core/`, `ai/`) requires **zero changes** for that migration
either \u2014 it was platform-free from day one, which is the architectural call
that makes this kind of long-term migration tractable at all.
